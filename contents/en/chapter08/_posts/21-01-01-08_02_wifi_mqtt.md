Estimated time: **~90 minutes**.

## Learning objectives

You will run a Mosquitto broker on your laptop, publish a velocity-style command on a private topic, and subscribe to a telemetry topic from an ESP32 on the same 2.4 GHz LAN. You will explain QoS 0 versus QoS 1 in one concrete failure (a retained “drive” message that survives a reboot), and you will keep the Chapter 08-01 serial timeout as the path that still stops the wheels when Wi-Fi drops. The lab log should show one received JSON command and one watchdog stop.

## Prerequisites

Lesson 08-01’s frame and timeout exist in your notes, even if the MQTT board test is still ahead. You can join the ESP32 to a 2.4 GHz network. You know an IP address from a port. Chapter 07’s motor wiring stays wheels-up. A Pico without Wi-Fi cannot do this lab; a Pico W can, but the commands below are the ESP32 Arduino / PlatformIO path because that is the board most Capstone kits in Vietnam actually ship.

## Why this sits on the path

ROS 2 is not MQTT, but the habits transfer. A topic name is a contract, a retained stale command is a loaded gun, and a transport that can vanish needs a local failsafe. When you reach Nav2, `cmd_vel` will also go quiet in a corner with bad Wi-Fi if you later put the robot PC on wireless. The watchdog you write here is the same idea as a ROS 2 deadline or a bridge that publishes zeros. Chapter 12’s learned policies are even less forgiving: a policy that outputs a chunk of motion still needs something underneath that drops torque when the link dies.

## Concepts

MQTT has three roles. The **broker** accepts TCP connections and fans messages out. A **publisher** sends a payload to a topic name. A **subscriber** receives whatever is published on the names it asked for. The broker in this lab is Mosquitto on your laptop, bound to the lab LAN, port 1883, with no anonymous access from the public internet. Do not port-forward 1883 on a home router.

Topic names for the Capstone robot:

```text
capstone/cmd      {"v": 0.20, "w": 0.00}
capstone/telem    {"vl": 0.18, "vr": 0.21, "batt": 11.6, "age_ms": 40}
```

`v` is forward speed in metres per second and `w` is yaw rate in radians per second, the same meanings ROS 2 will use in `geometry_msgs/Twist`. The ESP32 may still convert those to the −100…100 serial scale internally. Write that conversion in one function so Chapter 10 does not invent a second one.

QoS on MQTT is a delivery promise between one client and the broker. QoS 0 is at most once: fine for telemetry you will send again in 100 ms. QoS 1 is at least once: the broker may deliver a duplicate, so command handling must be idempotent (applying “v = 0.2” twice is fine; incrementing a counter twice is not). QoS 2 is exactly once and is more machinery than this robot needs.

The **retained** flag is the trap. A retained `capstone/cmd` is stored by the broker and handed to the next subscriber immediately. If the last retained payload was `{"v": 0.3, "w": 0.0}` and the ESP32 reboots, the robot drives as soon as it reconnects. For commands, publish with retain **false**, and publish an explicit zero on clean shutdown. For a static configuration topic, retain can be useful. Do not mix those habits.

Wi-Fi on the ESP32 is 2.4 GHz only for the classic DevKit. A 5 GHz-only SSID looks like “the password is wrong.” `MQTT_MAX_PACKET_SIZE` in older PubSubClient builds is 256 bytes; a large JSON status will silently fail to publish. Keep telemetry short.

The firmware rule that matters more than the library: store `last_cmd_ms` inside the MQTT callback, and in `loop()` if `millis() - last_cmd_ms > 300` force the motor command to zero. Parsing JSON must not be allowed to block the motor loop for tens of milliseconds. If `client.loop()` or a reconnect attempt takes too long, you will measure that damage in lesson 08-05.

## Worked example

Laptop broker and a manual publisher, before the ESP32 is powered:

```bash
sudo apt update
sudo apt install -y mosquitto mosquitto-clients
sudo systemctl enable --now mosquitto
ss -ltnp | grep 1883
mosquitto_sub -h 127.0.0.1 -t 'capstone/#' -v
```

In a second terminal:

```bash
mosquitto_pub -h 127.0.0.1 -t capstone/cmd -m '{"v":0.2,"w":0.0}'
```

The subscriber prints the topic and the JSON once. Publish a second message with `-r` (retain) and restart `mosquitto_sub`: the retained message appears immediately, with no new `pub`. That is the demo you will not use for `capstone/cmd`. Clear a retained payload with an empty retained message:

```bash
mosquitto_pub -h 127.0.0.1 -t capstone/cmd -r -n
```

PlatformIO `platformio.ini` for a typical DevKit:

```ini
[env:esp32dev]
platform = espressif32
board = esp32dev
framework = arduino
lib_deps = knolleary/PubSubClient@^2.8, bblanchon/ArduinoJson@^7
```

The callback only copies numbers and a timestamp. Motor code reads those globals. Pseudocode you should be able to map onto PubSubClient:

```text
on_message(topic, payload):
    if topic != "capstone/cmd": return
    parse v, w as floats
    if |v| > 0.5 or |w| > 1.5: return   # refuse a wild command
    left, right = diff_drive(v, w)      # lesson 08-04
    set_pending(left, right)
    last_cmd_ms = millis()

loop():
    if millis() - last_cmd_ms > 300: set_pending(0, 0)
    apply_pending_to_driver()
    client.loop()
```

Find the laptop’s LAN address with `ip -4 addr` and put that in the ESP32, not `127.0.0.1`. From the board, localhost is the board itself.

## Lab

1. Start Mosquitto. Confirm `ss` shows `0.0.0.0:1883` or your LAN address, not a public interface you do not control.
2. Subscribe with `mosquitto_sub -h <laptop-ip> -t 'capstone/#' -v` from the laptop.
3. Flash the ESP32 with your SSID, password, and broker IP. Open the serial log at 115200.
4. Publish `{"v":0.0,"w":0.0}` and then `{"v":0.2,"w":0.0}`.
5. Watch telemetry come back. Then stop publishing for one second.

**Expected serial log (shape, not exact numbers)**

```text
wifi ip 192.168.1.42
mqtt connected
cmd v=0.20 w=0.00 -> L=28 R=28
telem published
watchdog stop
```

**Expected subscriber line**

```text
capstone/telem {"vl":0.00,"vr":0.00,"batt":11.8,"age_ms":320}
```

Wheels-up: you should hear both motors nudge and then go quiet after you stop publishing. If they keep humming, the watchdog is not in the path that writes PWM.

**Failure modes**

| What you see | Likely cause |
| --- | --- |
| ESP32 never gets an IP | 5 GHz SSID, wrong password, or the AP isolates clients (“guest network”) |
| IP is fine, MQTT fails | Broker firewall, Mosquitto listening on localhost only (`listener` / `bind_address` in `mosquitto.conf`) |
| Robot drives immediately on boot | Retained command. Clear it with `mosquitto_pub -r -n` |
| Telemetry never appears | Packet bigger than the library limit, or you subscribed to `capstone/cmd` only |
| Motors stutter while connected | `client.loop()` plus DHCP reconnect blocking the 50 Hz loop. Lesson 08-05 |

## Exercises

1. Publish a retained `{"v":0.3,"w":0.0}`, reboot only the ESP32, and write down what the wheels do. Then clear the retain flag’s payload. Guidance: motion on boot means retain; after `-r -n`, boot must be stationary.
2. Why is QoS 1 acceptable for `capstone/cmd` while a retained message is not? Guidance: a duplicate of the same setpoint is harmless; a stored setpoint from yesterday is not a duplicate, it is a surprise.
3. Your JSON uses `x` and `z` one day and `v` and `w` the next. Which program is wrong? Guidance: both, until one schema is written down. Pick `v` and `w` and reject unknown keys.
4. Estimate how old a command may be if the ESP32 reconnects Wi-Fi for 2 seconds and the last payload was not zero. Guidance: without a watchdog, 2 seconds of the old PWM; with a 300 ms watchdog, at most one extra control period after the link dies, then zeros.
5. Sketch the two-line comment you will copy into the ROS 2 bridge: “MQTT is optional. Serial timeout is mandatory.” Guidance: that sentence is the whole point of the figure.
