Estimated time: about 45 minutes, most of it spent reading one installed XML file and writing down names you actually saw.

## Learning objectives

You will define a Sequence as "every child must succeed, in order" and a Fallback as "the first success wins," including what happens to children that are never ticked. You will connect those two control nodes to the recoveries you may have watched in the Nav2 tour: replan, spin, back up, clear a costmap. You will find the real XML under `nav2_bt_navigator` after the apt packages are installed, and you will explain why editing that file in place, or expecting the tree to write PWM, is a mistake.

## Prerequisites

The Nav2 tour in the previous lesson is the picture this one labels. You should remember that a goal in RViz became a path and then a `cmd_vel` Twist, and that the stack sometimes spins or backs up instead of pushing into a wall. You do not need a robot, a lidar, or a behavior-tree editor with a graphical canvas.

## Why this lesson sits on the path

The path is the Capstone base, then ROS 2 Jazzy, then Gazebo, then autonomy. The TurtleBot3 tour chased a goal because Nav2's receptionist is a behavior tree. Without the tree, a failed controller stops the robot until a human clicks again. With the tree, failure becomes a recovery and another attempt. Your bridge stays downstream of `cmd_vel`. The tree never becomes the H-bridge. This lesson only reads the policy the tour already ran.

## Concepts

A behavior tree is a tick-driven hierarchy. Something ticks the root many times a second. Each node returns a status: success, failure, or running. Control nodes do not move the robot. They decide which child is ticked next. Action nodes are the leaves that call into ROS: compute a path, follow a path, spin, wait, clear a costmap.

![A small behavior tree: a fallback tries a plan-and-follow sequence, and on failure ticks a recovery]({{ site.imgurl }}/generated/ch11_bt.png)

A Sequence ticks children from first to last. The first failure fails the Sequence, and later siblings do not run. Every child succeeding means the Sequence succeeds. A child that is still running keeps the Sequence running. Think of a checklist: compute a path, then follow it. A failed path computation means you never start following.

A Fallback ticks children in order and stops at the first success. Later children are not ticked. The Fallback fails only when every child has failed. That is "try the plan, otherwise recover." A ReactiveFallback keeps checking the earlier children, so a newly clear path can preempt a spin. Nav2 uses that so a goal update does not wait out a recovery that is no longer needed.

The navigate tree you will open on disk is longer than the sketch below, and it is the copyrighted project file, so this page does not paste it. The structure you should expect, in words, is a navigation branch that recomputes a path and follows it, wrapped so that failure falls through to recoveries. Those recoveries in Nav2's own trees are actions you can recognize by name once the file is open: spin in place, back up a short distance, and clear a global or local costmap that has become painted with phantom obstacles. The planner and the controller from the tour are leaves the tree ticks. They are not replaced by the tree.

The tree's leaves talk to ROS action servers. Follow-path ends in the controller publishing `geometry_msgs/msg/Twist` on `cmd_vel`. Spin and back up publish Twist as well, for a short, deliberate motion. Nowhere in that chain is a PWM duty cycle. If the Capstone wheels move during a recovery, it is because your bridge, or a simulated drive, subscribed to that Twist. Deleting the recovery branch to "simplify" the file makes the first blocked path a dead end. The tour looked clever because those leaves were still there.

BehaviorTree.CPP is the library Nav2 uses. The project site is the place to read what Sequence and Fallback mean in the library's own words. Nav2's getting-started pages are the place that ties that library to the navigator you launched. You do not need to vendor the library or write a C++ node this week.

Here is an original sketch, small enough to read aloud, and deliberately not the installed file. The comments name the real leaf types without copying their XML:

```xml
<root BTCPP_format="4">
  <BehaviorTree ID="CapstoneNavigateSketch">
    <ReactiveFallback name="NavigateOrRecover">
      <Sequence name="PlanThenFollow">
        <!-- Real trees put ComputePathToPose here and write a path. -->
        <!-- The next sibling is FollowPath, which tracks that path. -->
      </Sequence>
      <Sequence name="OneRecovery">
        <!-- Real trees put Spin, BackUp, or ClearEntireCostmap here. -->
      </Sequence>
    </ReactiveFallback>
  </BehaviorTree>
</root>
```

If plan-and-follow succeeds, the recovery sequence is not ticked. If it fails, the fallback ticks the recovery. A later tick can try the plan again because the control is reactive. A plain Fallback would still stop at the first success, without that re-check. The file on disk chooses. Write down what it chose.

## Worked example

Install the same Nav2 packages as the tour if they are not present, source Jazzy, and locate the package instead of guessing a prefix:

```bash
sudo apt install ros-jazzy-navigation2 ros-jazzy-nav2-bringup
source /opt/ros/jazzy/setup.bash
ros2 pkg prefix nav2_bt_navigator
```

The prefix on a stock apt install is `/opt/ros/jazzy`. The trees then live in:

```bash
ls /opt/ros/jazzy/share/nav2_bt_navigator/behavior_trees/
```

If the prefix command prints a different directory, because an overlay is sourced, list `share/nav2_bt_navigator/behavior_trees/` under that prefix instead. Do not hard-code a home directory path you have not printed.

Expected listing, the shape rather than a promise of every filename: one or more `.xml` files, and at least one name that contains `navigate`. Open one of those navigate files in a pager:

```bash
less /opt/ros/jazzy/share/nav2_bt_navigator/behavior_trees/navigate_to_pose_w_replanning_and_recovery.xml
```

If `less` says the file does not exist, run `ls` again and open the navigate-named file that does exist. Inside, find the first control node under the `BehaviorTree` element. That tag is the root control. Then search the file for recovery-looking leaves. You are looking for names in the spirit of `Spin`, `BackUp`, and `ClearEntireCostmap`. Quote two that are actually in the file you opened. If a name differs by a suffix, copy the suffix. The sketch on this page is not evidence.

## Lab

Do the worked example on your Jazzy machine. The deliverable is a short note with three parts.

1. The output of `ls` on the `behavior_trees` directory. Expected: a file list that includes an XML file whose name contains `navigate`. Paste the list.
2. The tag of the root control node in the navigate file you opened, copied from the file, plus the `name` attribute if it has one.
3. Two recovery actions you saw in that same file, copied by their tag names.

If `ros2 pkg prefix nav2_bt_navigator` fails, the package is not installed or the shell is not sourced. Apt install, source again, and only then conclude the path differs. If the XML path differs from `/opt/ros/jazzy/share/...`, the prefix command is the authority. Record the prefix you got.

| What you see | Likely cause | What to check |
| --- | --- | --- |
| `Package not found` | Nav2 apt packages missing, or setup file not sourced | The install and `source` lines, then `ros2 pkg prefix` |
| Directory missing under `/opt/ros/jazzy` | Overlay prefix, or a partial install | Use the printed prefix, then `ls` that share path |
| `ls` shows XML, none with `navigate` in the name | You listed the wrong folder | Confirm the path ends in `behavior_trees` |
| You edited the XML and the tour will not start | In-place edit, no copy | Restore from apt; copy to a workspace before any edit |
| Recoveries disappeared from your copy | They were deleted to "simplify" | The tour's spin and backup lived in those leaves |
| You expect the tree to twitch a GPIO | The tree ends in Twist, like Nav2 | PWM stays in your bridge |

Software only. There is nothing to buy, and a behavior-tree GUI is not required to read one file.

## Exercises

### Exercise 1

A Sequence has three children. On this tick the first returns success and the second returns failure. What does the Sequence return, and does the third child run?

**Guidance.** Sequence fails at the first failed child. The third child is not ticked. The answer is failure, with child three untouched.

### Exercise 2

A Fallback has three children: Spin returns failure, BackUp returns success, ClearCostmap has not been ticked. What does the Fallback return, and which children ran?

**Guidance.** First success wins. Spin ran and failed, BackUp ran and succeeded, ClearCostmap did not run. The Fallback returns success.

### Exercise 3

You want to experiment with removing Wait from a recovery list. Why is changing the file under `/opt/ros/jazzy` the wrong first edit, and where should a copy live?

**Guidance.** Apt owns that directory. A later upgrade overwrites it, and a syntax error breaks every launch. Copy into a workspace package and point the launch at the copy.

### Exercise 4

In two or three sentences, explain why a behavior tree does not drive PWM on the Capstone, even when a recovery spins the simulated TurtleBot3.

**Guidance.** Name the leaf, the Twist, and the bridge. The simulated robot has its own drive that subscribes to `cmd_vel`.

### Exercise 5

After `ls`, imagine the directory contains `navigate_to_pose_w_replanning_and_recovery.xml`. What will you write down from inside the file, and what will you refuse to copy from the sketch on this page?

**Guidance.** Write the real root control tag and two recovery tags from the file. Refuse to submit `NavigateOrRecover` unless that exact name is what you opened.
