Estimated time: **~90 minutes**.

## Learning objectives

You will write a URDF for a two-wheel base with a caster, separate visual, collision, and inertial tags, and load it through `robot_state_publisher` so the TF tree from lesson 09-05 appears without a hand-written static publisher. You will move one number (track width, wheel radius) into a xacro property and show that both wheel joints change together. You will also say which joint type a driven wheel uses (`continuous`) and which one a caster bracket uses (`fixed`), and why a pretty mesh with no collision tag is a ghost in Gazebo.

## Prerequisites

Lesson 09-05’s frame names, lesson 08-04’s $$L$$ and wheel radius, and a Jazzy desktop install so RViz can draw the model. XML well-formedness matters: a missing `</link>` fails the whole file. You do not need a 3D scanner. Boxes and cylinders are the right first model.

## Why this sits on the path

`robot_state_publisher` reads the URDF and publishes the static tree every other node expects. Gazebo Harmonic in Chapter 10 spawns that same file and adds physics. Nav2’s footprint is the collision outline you write here, not the acrylic photo. A learned policy does not consume URDF directly, but the robot you record data from in Chapter 12 still has joints, limits, and a base frame. If `base_link` in the URDF and `base_link` in the bridge disagree, every later frame is offset by a constant you will blame on SLAM. One file, one set of properties, xacro so you do not copy the left wheel by hand and forget to negate $$y$$.

## Concepts

A **link** is a rigid body. A **joint** connects a child link to a parent and says what motion is allowed. The tree has one root. For this base the root is `base_link`.

Joint types you need this week:

- `fixed` does not move. Caster bracket, laser mount, IMU board.
- `continuous` rotates without limit. Driven wheels. Do not use `revolute` with huge limits unless you enjoy a wheel that “hits the end stop” in the simulator.
- `revolute` is for a hinge with a lower and upper limit. That is an arm joint, Chapter 11’s MoveIt peek, not a wheel.

Each link can carry three different shapes. **Visual** is what RViz draws. **Collision** is what the simulator uses for contact. **Inertial** is mass, centre of mass, and inertia, which Gazebo needs before dynamics mean anything. A link with only a visual is drawable and physically weightless. A wheel with collision and no inertia often makes the simulator refuse the model or explode the time step. Copy a plausible mass: a small robot body of 1.5 kg, a wheel of 0.05 kg. Wrong by a factor of two is acceptable tonight. Wrong by a factor of a thousand (grams typed as kilograms, or a mesh in millimetres) is not.

The origin of a joint is the child’s pose in the parent, in metres and radians. Left wheel at $$y = +L/2$$, right wheel at $$y = -L/2$$, both with the spin axis along $$y$$ if the cylinder was built along $$z$$ and you roll it by $$\pi/2$$. Get the axis wrong and `continuous` spins the wheel like a coin instead of rolling. In the model below the visual cylinder’s axis is $$z$$, the joint origin rolls it so the axle is $$y$$, and `<axis xyz="0 1 0"/>` is the spin.

**xacro** is XML with properties and macros. A property:

```xml
<xacro:property name="track" value="0.16"/>
<xacro:property name="wheel_r" value="0.033"/>
<xacro:property name="wheel_w" value="0.02"/>
```

You reference it as `${track/2}`. Change `track` once when you remeasure the Capstone. The official tutorial [using xacro](https://docs.ros.org/en/jazzy/Tutorials/Intermediate/URDF/Using-Xacro-to-Clean-Up-a-URDF-File.html) shows macros; a property is enough until the file hurts to scroll.

`robot_state_publisher` subscribes to `joint_states` and publishes TF for every joint. Fixed joints publish even when `joint_states` is empty. Continuous joints stay at zero until something publishes a `sensor_msgs/JointState`. For a first RViz view, zeros are fine: the wheels exist, they just do not spin yet. Chapter 10’s diff-drive plugin is what will spin them.

Check the file before you launch it:

```bash
sudo apt install liburdfdom-tools
check_urdf <(xacro src/capstone_description/urdf/capstone.urdf.xacro)
```

**Expected:** a list of links and joints, root `base_link`, no “not well-formed” XML error.

## Worked example

Put this in `~/ros2_ws/src/capstone_description/urdf/capstone.urdf.xacro` after `ros2 pkg create capstone_description --build-type ament_cmake`. The package needs `urdf` and `xacro` dependencies and an install rule for the `urdf` directory. The model itself:

```xml
<?xml version="1.0"?>
<robot xmlns:xacro="http://www.ros.org/wiki/xacro" name="capstone">
  <xacro:property name="track" value="0.16"/>
  <xacro:property name="wheel_r" value="0.033"/>
  <xacro:property name="wheel_w" value="0.02"/>

  <link name="base_link">
    <visual>
      <origin xyz="0 0 0.05" rpy="0 0 0"/>
      <geometry><box size="0.18 0.12 0.06"/></geometry>
    </visual>
    <collision>
      <origin xyz="0 0 0.05" rpy="0 0 0"/>
      <geometry><box size="0.18 0.12 0.06"/></geometry>
    </collision>
    <inertial>
      <mass value="1.5"/>
      <inertia ixx="0.004" ixy="0" ixz="0" iyy="0.006" iyz="0" izz="0.008"/>
    </inertial>
  </link>

  <xacro:macro name="wheel" params="prefix y_sign">
    <link name="${prefix}_wheel">
      <visual>
        <geometry><cylinder radius="${wheel_r}" length="${wheel_w}"/></geometry>
      </visual>
      <collision>
        <geometry><cylinder radius="${wheel_r}" length="${wheel_w}"/></geometry>
      </collision>
      <inertial>
        <mass value="0.05"/>
        <inertia ixx="1e-4" ixy="0" ixz="0" iyy="1e-4" iyz="0" izz="1e-4"/>
      </inertial>
    </link>
    <joint name="${prefix}_wheel_joint" type="continuous">
      <parent link="base_link"/>
      <child link="${prefix}_wheel"/>
      <origin xyz="0 ${y_sign * track/2} ${wheel_r}" rpy="-1.5708 0 0"/>
      <axis xyz="0 1 0"/>
    </joint>
  </xacro:macro>

  <xacro:wheel prefix="left" y_sign="1"/>
  <xacro:wheel prefix="right" y_sign="-1"/>

  <link name="caster"/>
  <joint name="caster_joint" type="fixed">
    <parent link="base_link"/>
    <child link="caster"/>
    <origin xyz="-0.08 0 0.02" rpy="0 0 0"/>
  </joint>
</robot>
```

The caster link is empty on purpose so you see a fixed joint in the tree without a mesh hunt. Add a sphere visual when the empty link bothers you. Do not leave the driven wheels empty: Gazebo needs collision there.

Launch sketch, after the package installs the file:

```python
from launch import LaunchDescription
from launch.substitutions import Command, PathJoinSubstitution
from launch_ros.actions import Node
from launch_ros.substitutions import FindPackageShare

def generate_launch_description():
    xacro_file = PathJoinSubstitution([
        FindPackageShare("capstone_description"), "urdf", "capstone.urdf.xacro"])
    desc = Command(["xacro ", xacro_file])
    return LaunchDescription([
        Node(
            package="robot_state_publisher",
            executable="robot_state_publisher",
            parameters=[{"robot_description": desc}],
        ),
    ])
```

Then `rviz2`, Fixed Frame `base_link`, add a RobotModel display, and set the description topic to `/robot_description` if it is not already. **Expected:** a box and two cylinders, left and right, axles on $$y$$. `ros2 run tf2_tools view_frames` shows `base_link` as parent of `left_wheel`, `right_wheel`, and `caster`.

Change `track` from `0.16` to `0.20`, relaunch, and the wheels must move apart. If only one wheel moves, you hardcoded a coordinate and the property is unused.

## Lab

1. `check_urdf` on the expanded xacro. Paste the link list into `lab-notes.md`.
2. Launch `robot_state_publisher` and open RViz. Screenshot or a sentence: “two wheels, box body, fixed frame base_link.”
3. Set `track` to your measured $$L$$ from lesson 08-04. Rebuild or rely on xacro reading the source if you have not installed a copy. Confirm the wheel $$y$$ values with `tf2_echo base_link left_wheel`.
4. Delete the `<collision>` of `base_link` in a throwaway copy and write one sentence about what Gazebo will think the body is. Guidance you should reach on your own before Chapter 10: a visual with no collision does not hit walls.
5. Name the joint type you would use for a servo horn that may only move from $$-90^\circ$$ to $$90^\circ$$. That is the MoveIt peek, not this base.

**Failure modes**

| What you see | Likely cause |
| --- | --- |
| `robot_description` empty | `Command(["xacro ", path])` did not run, or the file is not installed in `share/` |
| Wheels inside the box | `origin xyz` uses centimetres, or $$z$$ is 0 so the axle is on the floor of the box |
| Wheel spins around the wrong axis in a later sim | `<axis>` not aligned with the cylinder after the `rpy` |
| `check_urdf` says the child link is missing | Macro parameter typo. Expand with `xacro file.urdf.xacro` and read the plain XML |
| RViz fixed frame error | You asked for `map`. This model has no `map` until SLAM |

## Exercises

1. Left wheel `tf2_echo` shows `y = -0.08` and you set `y_sign` of left to `+1` with `track` 0.16. What did you swap? Guidance: the sign in the macro call, or you are echoing the right wheel. $$+y$$ is left in REP-103.
2. Why is the caster `fixed` even though it swivels on the real robot? Guidance: for this course the caster is not actuated and you are not modelling its swivel. A fixed joint keeps a frame. Modelling the swivel is extra, and it is not a drive wheel.
3. Visual mesh is 1000 times too big. Which tag did you forget to scale, and what is the usual cause? Guidance: the mesh was exported in millimetres. Scale the mesh or the visual origin. Collision must get the same scale or contact happens a metre away from the drawing.
4. `joint_states` never arrives. Where are the wheels in RViz? Guidance: at the zero angle of a continuous joint. The link is still there. Spinning comes from a publisher, which Chapter 10 adds.
5. Write the single xacro property name you will refuse to duplicate in the bridge YAML. Guidance: `track` / `track_width`. One measurement, two consumers, and they must be the same metres.
