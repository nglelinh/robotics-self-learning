Estimated time: **~90 minutes**.

## Learning objectives

You will publish a static transform from `base_link` to `laser`, echo it with `tf2_echo`, and draw the REP-105 chain `map → odom → base_link → sensors` from memory with the name of the node that should own each edge. You will recognise two publishers on the same edge as a bug, and you will place a camera optical frame instead of pretending the camera looks along $$+x$$. Wheel odometry from Chapter 08 becomes the `odom → base_link` edge only after this vocabulary is stable.

## Prerequisites

Lesson 09-02’s topics, and lesson 08-04’s body frame: $$+x$$ forward, $$+y$$ left, $$+z$$ up, positive yaw a left turn. You can run two terminals with Jazzy sourced. RViz is installed if you took `ros-jazzy-desktop`. No lidar is required; a static publisher stands in for the sensor mount.

## Why this sits on the path

A laser point is a range and a bearing in the laser’s frame. A goal is a pose in the map. Nav2, SLAM, and a vision node do not “just know” where the sensor is bolted. TF2 is the shared tree that answers “where was frame A in frame B at time t.” If you name the laser `laser_link` in the URDF and `scan` in the bridge, the scan is a set of numbers with no address. If two nodes both publish `odom → base_link`, the robot jumps in RViz and the costmap smears. Chapter 10’s simulator and Chapter 11’s SLAM will not invent this tree for you. The Capstone’s measured sensor offsets belong here, in metres, before anyone tunes a planner.

## Concepts

A frame is a named right-handed coordinate system. A transform is a translation plus a rotation that takes points from a child frame into a parent frame. TF2 stores those edges with timestamps. You query them. You do not hard-code “the lidar is 8 cm forward” inside the SLAM node and again inside the detector.

[REP-105](https://www.ros.org/reps/rep-0105.html) fixes the mobile-base names this course will use:

- `map` is the world frame SLAM or localization owns. It may jump when the map corrects drift.
- `odom` is a smooth frame that starts where the robot started. It is allowed to drift. It is not allowed to jump.
- `base_link` is attached to the robot body, typically at the axle midpoint for a diff-drive, with $$+x$$ forward.
- `base_footprint` is the projection of `base_link` onto the ground. Useful, optional for a first model.
- Sensor frames (`laser`, `imu_link`, `camera_link`) hang off `base_link` and are usually static.

Who publishes which edge:

| Edge | Publisher | Character |
| --- | --- | --- |
| `map → odom` | SLAM or AMCL, later | May jump |
| `odom → base_link` | Wheel odometry (your bridge or a controller) | Continuous |
| `base_link → laser` | URDF via `robot_state_publisher`, or a static publisher | Fixed bolt pattern |

One parent, one broadcaster, per edge. A second odometry node “to compare” will fight the first unless you put the comparison on a different child frame such as `odom_raw`. Do not publish both into `base_link`.

Time matters. A scan stamped 200 ms in the past needs the transform that was true then, not the transform that is true now, if the robot is turning. TF2 keeps a buffer for that. If the buffer does not contain the stamp, you get an extrapolation error. The usual causes are: the odometry stopped, the stamps use a different clock (`use_sim_time` on one node only), or the scan’s `frame_id` is a name nobody publishes.

Camera frames have a second convention. [REP-103](https://www.ros.org/reps/rep-0103.html) says a body frame looks along $$+x$$. An optical frame looks along $$+z$$, with $$+x$$ right and $$+y$$ down, because that is how image rows work. `camera_link` can follow the body convention. `camera_optical_frame` is the frame you put in an `Image` message’s `frame_id`. Swapping them makes a “left” pixel command a right turn. The rotation from link to optical is a fixed transform: roll $$-\pi/2$$, then yaw $$-\pi/2$$, which you can publish once and then stop thinking about it.

Units are metres and radians. A “5” that means five centimetres will place the laser inside the axle and every cloud will look like a ball around the robot.

## Worked example

The Capstone carries a tiny lidar 5 cm forward of the axle centre, 8 cm up, pointing forward. No roll, no pitch, no yaw relative to `base_link`. Publish that as a static transform:

```bash
ros2 run tf2_ros static_transform_publisher \
  --x 0.05 --y 0.0 --z 0.08 \
  --roll 0 --pitch 0 --yaw 0 \
  --frame-id base_link --child-frame-id laser
```

Second terminal:

```bash
ros2 run tf2_ros tf2_echo base_link laser
```

**Expected**, repeating at a few hertz:

```text
At time ...
- Translation: [0.050, 0.000, 0.080]
- Rotation: in Quaternion [0.000, 0.000, 0.000, 1.000]
```

The echo order is parent then child: “where is `laser` in `base_link`.” If you swap the names, the translation comes back negated, which is a useful check and a common accident.

View the tree:

```bash
ros2 run tf2_tools view_frames
```

That writes a `frames.pdf` (and a `.gv`) in the current directory. Open it. You want a single arrow from `base_link` to `laser`. Two arrows into `laser` means two publishers.

A point 1 m in front of the laser is $$(1, 0, 0)$$ in the laser frame. In `base_link` it is about $$(1.05, 0, 0.08)$$. You do not add those numbers by hand in Nav2. You ask TF. The manual add is only the sanity check that the static numbers are in metres.

Optical frame, if you already own a camera and want the name reserved:

```bash
ros2 run tf2_ros static_transform_publisher \
  --x 0 --y 0 --z 0 \
  --roll -1.5708 --pitch 0 --yaw -1.5708 \
  --frame-id camera_link --child-frame-id camera_optical_frame
```

Do not attach the optical frame to `base_link` and also attach `camera_link` to `base_link` with a different offset unless you enjoy two cameras in RViz. Chain them: `base_link → camera_link → camera_optical_frame`.

## Lab

1. Publish the static laser transform with your real offsets. If you have not measured yet, use the 5 cm / 8 cm example and write “unmeasured” in the notes. Measure later with the same tape as lesson 08-04.
2. `tf2_echo` until the translation matches what you typed, to millimetres.
3. `view_frames` and keep the PDF in the lab folder.
4. Start a second static publisher with the same parent and child but `--x 0.5`. Echo again. **Expected:** the transform flips between 0.05 and 0.5, or RViz (if you add a TF display) jitters. Kill the intruder. This is the failure mode you will recognise when two odometry nodes fight.
5. Optional RViz: `rviz2`, add a TF display, set Fixed Frame to `base_link`. You should see the `laser` axes 5 cm forward. If the fixed frame is `map` and you have no `map`, RViz complains. That complaint is honest. You have not started SLAM.

**Failure modes**

| What you see | Likely cause |
| --- | --- |
| `tf2_echo` waits forever | Frame names differ by a character, or the publisher died. `ros2 topic echo /tf_static --once` shows the raw message |
| Axes point backward | Yaw of $$\pi$$, or you measured “forward” toward the caster |
| Extrapolation error in a later node | Stamps in the future, or one node on sim time. Compare `header.stamp` with `ros2 topic echo /clock` only after Gazebo |
| Tree has `base_link` twice | Two publishers. `view_frames` is the picture; `ros2 topic info /tf -v` shows the nodes |
| Camera “turns the wrong way” | Image `frame_id` is `camera_link` while pixels are in the optical frame |

## Exercises

1. Echo says translation `[0.05, 0, 0.08]` and you wanted the laser on the centreline. Which number is the sideways error? Guidance: the middle one, $$y$$. Zero means centred.
2. Why may `map → odom` jump while `odom → base_link` must not? Guidance: the map edge is a correction. The odom edge is what controllers integrate. A jump there looks like the robot teleported and the local planner kicks.
3. Two nodes publish `odom → base_link`. You want both estimates. How do you name the second child? Guidance: not `base_link`. Use something like `base_link_ekf` only if a single fusion node is the one publishing the real edge. A raw second stream can use `odom_enc` as a different parent or a debug child that nothing else uses.
4. A scan `frame_id` is `laser_frame` and the URDF says `laser`. What does TF report? Guidance: a disconnect. The names are the API. Pick one and change the other.
5. In one sentence, where does lesson 08-04’s $$v, \omega$$ enter this tree? Guidance: integrate them to a pose and publish that pose as `odom → base_link`. The static laser edge does not contain velocity.
